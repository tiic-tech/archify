# PRD workspace

Use this route when the user requests a structured requirements workspace, a revision-bound reader or an editable Markdown PRD. It is not the ordinary native-diagram or one-page-explainer route. The authoritative source is a typed JSON workspace, its authored profile and associated local assets, not an exported README, HTML, PDF or browser journal. Read `schemas/prd-workspace.schema.json` before authoring; model actual sources, evidence, relationships, roles and unresolved gaps rather than inventing requirements or confirmations. Native diagrams remain the existing Archify diagrams bound to modeled objects. Do not treat a PRD export as a source model or promise automatic Markdown-to-model synchronization.

Replace `bin/archify.mjs` with the installed Skill's path. All examples use new, unoccupied outputs; a failure must not be reported as a successful delivery.

```sh
node bin/archify.mjs prd validate MODEL.json --json
node bin/archify.mjs prd compile MODEL.json -o NEW_MANIFEST.json --json
node bin/archify.mjs prd build MODEL.json -o NEW_READER.html --audience internal --json
node bin/archify.mjs prd export MODEL.json -o NEW_DIRECTORY --audience internal --markdown-only --json
```

Source drafts may use `{ "question": "questionId" }` instead of a concrete predicate only for a binding's `detail.visibility`, `detail.editable`, or `detail.required`. The existing question must explicitly scope or target the binding or its containing section, variant, interface or activity; if both scope and target are present they must agree on that context. Do not guess a constant when behavior is unknown. These cells block readiness at their binding path even for a nonblocking question. Internal compilation, reader and export retain the located TBC and its question; these are draft facts, not executable policy. For a standard field row, an unknown required or editable predicate requires its exact question in `required` or `editableWhen`, respectively; do not replace it with known prose or a different question. Client projections can represent these cells only when the Question and a relevant binding or explicitly disclosed ancestor context are approved; the output uses the Question's public alias and remains TBC. Question scope and target must intersect on an approved context: omission explanations are not identifiers. A v2 Feature policy must also bind the approved source binding and its Questions with `bindingSourceSha256` on the binding's object approval. Compute it from the compiled source using `bindingPublicApprovalV1(model, binding)` from `explainer/workspace/prd-model.mjs` after independently reviewing the source and public facts. Changed binding or Question facts invalidate that approval; updating a digest alone is not review or business confirmation. A Service export checks the bindings in its selected and actually referenced review dependencies, while a whole-workspace export checks all projected binding approvals. A public review snapshot checks its own semantic dependency closure. Keep this source-bound digest and policy private. V1 role-oriented and non-standard v2 Feature client product documents still reject these cells. Rule conditions and other predicates do not accept this form.

`compile` records a semantic revision, selected components, verified local assets, prepared native diagrams and code/schema identities. To check an established ancestry, pass `--base-manifest OLD_MANIFEST.json --expect-revision OLD_REVISION`; `--ready OBJECT_ID` also checks scoped readiness. A declared gap or technical review flag is not an approval. Keep the authoritative model, sources, assets and previous manifest; internal material may contain private source text, paths, image bytes and history.

The reader's **Download Markdown package** is a whole-workspace frozen same-revision ZIP with a manifest and allowed assets. For v2, the manifest names the editable primary Markdown and `README.md` is an index; legacy packets use `README.md` as their main document. The reader has no Service-history input and does not claim a Service-authored log. Profile `documentLayout` is optional: absent or `inline` retains the existing complete inline PRD and full print. `referenced` produces a main PRD plus `appendix.md` with stable full-fact anchors; the default HTML export also includes `appendix.html`. Keep the sidecars and assets together. In that layout the reader and PDF print the main PRD only; download the Markdown package for the appendix. Native diagrams may be overviews: use their linked vector and structured facts for detail. Cross-file companion references in PDF are plain text, not clickable file actions; use the accompanying Markdown/HTML package. Same-document PDF navigation remains available. The profile is part of the revision and export identities. Print does not depend on currently open cards. `prd export` without `--markdown-only` also emits HTML; `--pdf` requests a sandboxed Chromium PDF and cannot be combined with `--markdown-only`. Markdown is primary; HTML and PDF are projections, not a source for Markdown. Outputs are create-only: use a new filename or directory, retain old artifacts and check the JSON receipt. Directory publication currently requires Linux/GNU `mv`; do not promise unsupported cross-platform behavior.

## Feature-centric authoring contract (v2)

`profile.productDocument.version: 2` opts into the closed Feature contract in `schemas/prd-workspace.schema.json` (`productDocumentV2` and related definitions). A complete unrelated example is [`examples/prd-equipment-workspace.json`](../examples/prd-equipment-workspace.json). The workspace itself remains schema v1. Prefer v2 for new Feature-first functional baselines; v1 product documents retain their existing role-oriented compatibility behavior. V2 supports whole-workspace Markdown, HTML/PDF and reader builds, plus Service `--markdown-only` packets. The reader's Feature correspondence identifies its source Service, integrated native workflow and named Markdown anchor. Opening a Service with one detailed Feature selects that workflow; explicit view deep links take precedence. When a Service has multiple detailed Features, no workflow is selected automatically: choose the intended Feature workflow in its Service context or choose a native view explicitly. Catalog-only entries remain TBC. Validate and review each packet; the example is synthetic and is not business confirmation.

The optional `profile.productDocument.standard.version: 1` adds the closed standard sections to each Feature on that same graph; see [`examples/prd-equipment-standard-workspace.json`](../examples/prd-equipment-standard-workspace.json) and the schema. For standard Features, the reader mounts the same Feature-numbered native workflow used by the packet and print view. If multiple Features share a native view, choose a Feature: an old view-only link does not arbitrarily select numbering. A view with a single standard presentation retains old view links. Public presentations are rendered from the independently approved public plan and view, not private labels. Required gaps in a referenced external Feature business rule block readiness of the using Feature or Service, at the rule owner's locator; unrelated owner content is not imported. Readiness and hashes do not confer business confirmation.

A document has an authored portable lowercase `key`, a lowercase language tag, and ordered modules, subModules and Features. Each Feature has a globally unique presentation `id`, a unique portable `key`, title and source `service`; several Features can share one Service. `catalog-only` requires a Service-scoped `question` and has no workflow or actions. `detailed` requires a reviewed purpose/boundary `summary` citing at least the owning Service, one native workflow and ordered actions; each action binds an actual Service activity. Set each action's `performer` explicitly to `user`, `system`, or `external`: an external human or external system is not a full-function internal user. `user` requires a modeled human activity and `system` a modeled system activity; `external` can be either. The workflow must bind every activity in that Feature. Review the actual native topology, outcomes and branches; bindings alone do not prove business completeness. No role chapter or invented login is required. A modeled activity may have pages used by that activity and their modeled variants; system/external operations may have no page. Preserve actual actors, handoffs and unknowns in the model rather than treating the documentation viewpoint as authorization.

Each action and page can contain explicit semantic groups. A group has a presentation `id`, title, `sources` (typed field, binding, element, action, rule, integration, state, transition, entity, evidence, decision or acceptance IDs), and reviewed summary; optional `fields` and `rules` are concise authored strings reviewed against the same source set, and optional `questions` reference scoped modeled questions. When a Service has detailed Features, its modeled activities, used interfaces/variants, and applicable fields, bindings, elements, actions, rules and questions must be covered; a sibling page cannot cover another page's requirements. An action's own pages can cover its action requirements without repeating them in an action group. Predicate-only fields are review dependencies, not necessarily displayed controls. A page with no variant is an entry placeholder when that activity models variants of the same interface; it does not inherit their contents. Group sources must be connected to the action/page; rules must apply to its context. A Service with only catalog-only Features does not claim detailed completeness. A catalog-only Feature in a mixed Service is not proof that an existing modeled activity is detailed. Fine-grained source facts remain authoritative and are not business-confirmed merely because a summary is authored.

A `summary` is `{ "text": "...", "reviewed": [{ "object": "...", "sha256": "..." }] }`. Its review set includes the Feature's Service, action activity, or every group source and their transitive typed actor, uses, variant, action, integration, field, rule, entity, state, from/to, rule/exception scope and predicate-field dependencies. Each digest is SHA-256 over UTF-8 canonical JSON of the **whole audience-specific object**: recursively sort object keys, retain array order and serialize with JSON encoding. Any change to a reviewed object yields a located stale-summary diagnostic; missing dependencies and duplicate review entries also fail. Prose and hashes must be reviewed together: regenerating a digest alone is not review, business confirmation or approval. For authoring convenience `snapshotReviewedTextV2(objects, text, ids)` in `explainer/workspace/prd-product-v2.mjs` builds the dependency list and hashes from the supplied objects; `normalizeProductDocumentV2(plan)` canonicalizes object-key order without reordering arrays. Neither validates intent. Example use after examining the cited facts:

```js
import { snapshotReviewedTextV2 } from './explainer/workspace/prd-product-v2.mjs';
const summary = snapshotReviewedTextV2(model.objects, 'Reviewed concise description', ['fieldId', 'ruleId']);
```

For preparing an independent client plan, the author-side `snapshotPublicReviewedTextV2(manifest, policy, text, sourceIds)` export in `explainer/workspace/prd-product-public-v2.mjs` uses the actual allowlisted projection and returns `{text, reviewed}` with source IDs for the private policy plan and hashes of public-aliased approved facts. It rejects missing required detail, unapproved semantic relations and unprojected dependencies; omission prose is never an ID. A binding's referenced Question is reviewed as an approved public fact, but its unrelated scope and target contexts are not imported as binding dependencies. An explicitly reviewed Question on its own retains its ordinary context requirements. Private status, review lineage and withheld explanations are not hashed. It does not approve the text or validate a complete public plan or view topology. Keep the source-ID plan and policy private. Example after compiling the source manifest and separately approving policy values:

```js
import { snapshotPublicReviewedTextV2 } from './explainer/workspace/prd-product-public-v2.mjs';
const publicSummary = snapshotPublicReviewedTextV2(manifest, policy, 'Independently reviewed public text', ['sourceFieldId']);
```

Client v2 export and reader build require a separately authored `policy.productDocument` v2, approved objects and approved native views. For a standard public Feature with screens, canonical matching requires a unique source Feature with the same Service and workflow view, matching activity and interface/variant/page context. If a rich internal view is incompatible with public native preparation, retain it but select an independently authored compatible view as the canonical Feature workflow and use that same source view in the public Feature plan; recheck bindings, process semantics and summaries. A page-free Feature's alternate view is not evidence that arbitrary screen-bearing workflow variants match. Validation uses projected facts and public review hashes, verifies their semantic paths and dependencies, and remaps source references only after validation. Private values, source hashes and omission explanations are not aliases or fallbacks. Question contexts retain only explicitly approved actual targets. The internal `projectPublicFeatureDocument(manifest, policy, projection, publicViews)` helper consumes the prepared, explicitly approved projection and views and returns `{ plan, objects }` with public aliases; invalid plans throw located diagnostics. It is an export pipeline helper, not an approval or a standalone authoring command. Use `snapshotPublicReviewedTextV2` for authoring reviewed bindings as described above. The schema validates structure, not narrative truth; review workflow topology, grouped conditions, exceptions, state changes and question placement before delivery.

A v2 packet's stable primary name is `<key>.prd.<client|internal>.<language>.md`: use the single Feature's key when a Service packet contains one Feature, otherwise the collection key. `README.md` is an index; `appendix.md` is the audit companion. `manifest.json` records `primaryMarkdown`, `auditMarkdown`, `features` (each `id`, `key`, `anchor`, `service`, `status`, `artifact`, and, for detailed Features, `workflow` and `workflowAsset`), `assets`, and SHA-256/byte metadata in `artifacts`. Feature anchors resolve in the named primary, and workflow assets are local paths. The audit includes the explicit semantic group/source map and raw approved facts. Internal audit facts can contain private sources; client audit uses approved projection only. Do not edit a prior packet in place: Service base loading verifies every recorded artifact, including legacy `README.md` bases and new primary/index files, before reuse and again before create-only publication. Authored history prefixes remain mandatory.

## Role-oriented product documents

An optional `profile.productDocument` (schema version 1) selects a role-oriented PRD rather than the legacy component layout. Read the closed `productDocument`, `productUseCase`, `productPage` and `productWorkflow` definitions in the workspace schema. Author ordered Services, features, role chapters and use cases using stable model IDs and distinct presentation anchors. Every selected Service activity needs a use case, every modeled activity actor needs a role chapter, and each use case belongs to one modeled role; system roles do not acquire invented login or dashboard steps. Place selected fields, bindings, UI elements, actions and rules in the relevant task/page, and place explicitly targeted or scoped local questions near the related task, page or edge case, or resolve the located coverage diagnostics. A listed single-field control can be folded into a unique same-container binding without losing its facts; an unscoped control can share the explicitly authored page variant, while explicitly scoped controls must match it. Report columns remain separate. Evidence, sources and decisions may remain audit-only. The main document explains the technical-review flag once, and marks affected facts and owning summaries without changing their business status or treating review as approval. Product HTML/PDF and the reader print view share scoped print typography; the Feature List uses proportioned columns without moving requirements out of the main document. Element / Rule cells derive structured descriptions, explicitly related fields, conditions, rules, scoped exceptions, operations and open points from typed facts. Only modeled groups are shown, and public cells use only the approved projection. Simple binding flags share their field item; exact repeated binding/control context and gaps are factored only within the current page or task, naming the affected fields. Distinct facts remain in their own context. Every explicitly used interface and variant must appear as a page context in a use case for that activity, even if the page currently has only a description. Coverage is the union across that activity's use cases; pages must be used by their activities and variants must match their pages and activity context. Reuse explicitly references an earlier emitted page anchor. Page-free tasks are valid when no page is modeled.

The Service workflow is the complete modeled business swimlane: every supplied overview view must bind the Service plan's activities. A role chapter starts with its own native workflow, followed by responsibilities, journey, pages/operations, and questions/acceptance; each supplied role view must establish the role and bind all activities assigned to that chapter. Missing workflows and prototypes are explicitly identified, not invented. Internal prototype captions retain any authored asset limitations beside the image; public captions use only separately approved wording. Coverage validates the bindings, not the business completeness of the topology; review diagrams and prose. Native views remain source-backed and the schema permits up to 128. Whole-workspace Markdown, HTML/PDF and the frozen reader package use the same composition; Service exports use it when a plan is present. They include a separate technical appendix. Service history is used only when explicitly provided; whole-workspace and reader exports say when no authored history is available.

For client product documents, author and review an independent `policy.productDocument` of the same shape, using source IDs for references and public-only prose throughout. All needed objects, facts, parents, relationships, scoped references and predicate dependencies must be explicitly disclosed; an omission explanation is not an alias. Referenced workflows need a separately approved public view, and prototypes require individually approved distributable assets. A field property explicitly withheld with a public explanation is shown at that field as not disclosed; it is not replaced with the private value or treated as an identifier. Missing public plans or genuinely required dependencies fail closed; nothing falls back to the private plan. Explicitly omitted private-only requirements do not count toward public coverage. The Service technical appendix and identity include all selected approved evidence and context, not just objects cited by the product plan. Carefully review all approved prose, nested facts, diagram topology and complete image bytes. The stable opaque workspace UUID is part of the public feedback protocol; client readers retain it along with revision, disclosure, snapshot and exporter identities so public feedback can be mapped against the exact model and policy.

## Service-scoped Markdown and authored history

Service export is explicitly opt-in and requires a stable schema-v1 `workspaceId`, a typed Service ID, an audience-specific authored history file and `--markdown-only`:

```sh
node bin/archify.mjs prd export MODEL.json -o RELEASE_1 --audience internal --service SERVICE_ID --service-history HISTORY.json --markdown-only --json
node bin/archify.mjs prd export MODEL.json -o RELEASE_2 --audience internal --service SERVICE_ID --service-history HISTORY.json --incremental-from RELEASE_1 --markdown-only --json
```

An example history (replace the Service ID, dates and statements with real authored values):

```json
{
  "schemaVersion": 1,
  "service": "serviceId",
  "audience": "internal",
  "entries": [
    {"version": "1.0", "date": "2026-10-30", "summary": "Initial research baseline", "author": "Research team", "references": ["decision-1"]},
    {"version": "1.1", "date": "2026-11-02", "summary": "Clarify the shared field rule"}
  ]
}
```

Entries are ordered, versions are unique, dates are real ISO calendar dates, and summaries, optional authors and optional reference strings are explicitly authored; they are not approval claims. Supply `author` only when the history actually records it. When some entries have an author and others do not, the missing authors are shown as not recorded. The first export needs at least one entry. With `--incremental-from`, retain the previous entries exactly and append an entry when the Service projection/recipe changes. An explicitly authored editorial entry is allowed without a content change. A cold export without a base cannot verify ancestry; keep the prior packet and use it as the base when continuing a lineage. Client history is a separate input whose contents are intentionally approved for public distribution; the internal history is never copied automatically. The input Service ID is replaced by its approved alias in client artifacts. Review all public policy and history text before distribution.

The original model and client policy are validated and projected before Service selection. The selected Service's explicit ownership, relationships, predicates and scoped records provide context; referenced other-Service objects are context only and do not expand their owned branches. A native view explicitly associated with that Service also contributes its bound objects, direct drill targets, lane roles and source as reading context, including unowned lifecycle states and their real dependencies; this does not create ownership. An unowned typed transition is also shared reading context when it has exactly one `from` and one `to` state and both endpoints are already selected and non-foreign; its existing forward references, predicates and provenance are then traversed normally. This inverse rule does not select a missing endpoint, infer ownership, or follow arbitrary inverse relationships. Incomplete or ambiguous endpoints do not qualify. Client transition facts and public provenance descriptions remain subject to explicit disclosure; private source originals and locators are never projected. Interfaces used by selected activities supply shared descendants, except variants explicitly used only by another Service; unscoped shared descendants remain shared context. This is not a claim that another Service is complete. Native views containing other-Service owned bindings are omitted and do not seed this context. Views without an explicit Service association retain the existing bounded inference from Service-owned bindings; an unrelated view does not seed context. Explicit questions about a reached actor are included as shared context when their scope and target agree; a role does not become an ownership root, and questions explicitly scoped only to another Service stay outside this document. Components follow the Profile and the applicable full fact appendix remains available. Unmodeled relationships and disclosure gaps retain their existing qualification; the document is a technical export, not customer confirmation.

The complete packet contains `README.md`, optional `appendix.md`, assets, `manifest.json` and derived `cache/` files. V2 additionally names its primary Markdown in the manifest; README is an index, not the main PRD. Keep them together. Client values come only from the approved public projection. V2 reuses unchanged action and page blocks independently; caching is not incremental preparation. Cache hits bypass unchanged component or product-block rendering and native SVG assembly, but model validation, native preparation, disclosure projection and product IR composition still run; CLI `cache` counts and stage `timingMs` are execution measurements, not deterministic artifact identities. Keys include renderer recipe, component context and anchor allocation. Service record object keys are normalized before rendering; authored array order remains unchanged. The Service projection identity is independent of the global workspace revision and presentation camera, but binds the Profile, relevant content and renderer/schema/native runtime. Authored native visual changes can change that identity even if business meaning is unchanged.

In the author-side CLI JSON, `revision` is the Service document identity, `workspaceRevision` is the original prepared workspace/model revision, `historyIdentity` binds the authored entries, and `baseReceipt` is the exact prior manifest's byte hash (or null for a cold export). Keep this receipt privately: its workspace lineage and diagnostics are not a client delivery. The deterministic packet does not embed `workspaceRevision` or `baseReceipt`; its parent history identity is derived from the authored history prefix.

Before reuse and immediately before create-only publication, the exporter verifies the bounded base manifest and every tracked file. Edited, missing, unsafe or symlinked tracked files fail without replacing the base or destination, including derived cache files; incompatible cache recipes perform a full rebuild. Choose a new immutable directory for every export and manage a stable pointer separately; do not edit a previous packet in place expecting synchronization. The manifest's SHA-256 values detect accidental corruption and bind content, but are not signatures or authenticity guarantees. Service export does not accept `--pdf`, `--ready`, `--expect-revision` or `--base-manifest`; other existing export and reader commands remain whole-workspace operations.

## Client disclosure

A client reader or export requires a private author-authored disclosure policy:

```sh
node bin/archify.mjs prd build MODEL.json -o NEW_CLIENT.html --audience client --disclosure POLICY.json --json
node bin/archify.mjs prd export MODEL.json -o NEW_CLIENT_DIRECTORY --audience client --disclosure POLICY.json --markdown-only --json
```

The policy explicitly approves public component headings, object aliases, title/purpose, whole selected properties, relations, omission/withholding explanations and distributable images. For example, this minimal policy applies only to a model whose selected object IDs and component IDs match it:

```json
{
  "version": 1,
  "components": {"catalogSection": "Seed catalog", "notes": "Notes"},
  "objects": {
    "name": {"id": "packetName", "title": "Packet name", "purpose": "Identify a packet", "fields": ["detail.dataType"]}
  },
  "omitted": {"garden": "The broader scope is under review.", "catalog": "The boundary is under review.", "extra": "The note needs further interpretation."}
}
```

For other models, each included non-source object needs an approved object or an omission explanation; each authored detail/rule/gap/content/priority needs an approved field or `withheld` explanation. Approve parent and typed relations explicitly; undisclosed targets need `omissions` explanations. Optional `assets` maps internal IDs to `{id,caption}` for distributable attached PNG, JPEG or WebP. Optional `views` requires complete explicit public aliases and topology for the supported native subsets; unsupported shapes fail closed. Follow located diagnostics rather than guessing mappings. The policy is an allowlist, not automatic redaction: review all allowed prose, nested values, topology and complete image bytes before delivery. The reader is non-authoritative; only explicitly mapped workflow and lifecycle subsets can produce public native views, and unsupported or unmapped views are gaps or fail closed. Keep the private policy, model, author-side receipts and reverse mappings out of client deliveries. A hash or `distributable` flag is not disclosure authorization.

### Public native views: edges and legends

A supported workflow view policy supplies `id`, `title`, `caption`, `context`, `version`, `sourceVersion`, complete `lanes` and `nodes` maps, and optionally the exact source `service` when it is projected. Each lane/node mapping is keyed by its private source ID and contains only `{id,label}`; every node must bind one projected object and every lane one projected role. The following is an **excerpt** for a fictional workflow whose two source edges have stable IDs `draftToReview` and `reviewToDraft`; the rest of that view and policy must also be complete:

```json
{
  "edges": {
    "draftToReview": {"id": "publicEdgeA", "label": "Send for review"},
    "reviewToDraft": {"id": "publicEdgeB", "label": "Request changes"}
  },
  "legend": {"mode": "auto", "entries": {
    "frontend": {"label": "Participant step"},
    "backend": {"label": "Review step"}
  }}
}
```

When `edges` is supplied, **every** source edge needs a unique, stable source `id` and exactly one `{id,label}` mapping; public labels are required even for an unlabeled source edge. Public edge IDs must be portable and unique among the view's public lanes, nodes and edges. Directed endpoints and parallel edges are preserved. Native `role` (`main`, `branch`, `async`, `return`, `error`) and `route` enums are retained exactly from the source when authored; they cannot be overwritten in the policy. They need disclosure review: role is structural meaning, while route is a native routing choice, not a public prose label. Source edge fields beyond `id`, `from`, `to`, `label`, `role` and `route` fail closed, including custom geometry, variants and arbitrary metadata. Source labels and IDs are not automatically copied. A workflow with a source label, role or route requires explicit edge mappings; a missing source ID is a located error. Legacy simple unlabeled edges with no role/route still work without `edges`: they receive generated `edge1`, `edge2`, … IDs in source order, independent of any source ID. These generated IDs are order-dependent, not stable mappings. Both native workflow schema versions are supported only within this bounded subset and subject to native validation.

A lifecycle uses complete `states` and `transitions` maps keyed by private IDs with `{id,label}` values, and requires an explicitly projected source `service`; its supported source subset is narrower than the full native schema. For either supported kind, optional `legend` is entirely public policy input, never the source legend. It accepts the native `mode` (`auto`, `all`, `hidden`) and `entries` map of supported kinds, each containing only `label` (nonempty, at most 80 characters) and/or boolean `visible`. Workflow kinds are `frontend`, `backend`, `database`, `cloud`, `security`, `messagebus`, `external`; lifecycle kinds are `start`, `active`, `waiting`, `decision`, `success`, `failure`, `neutral`, `external`. The native entry contract has no note field; do not put private notes or arbitrary HTML/colors in it. Omission keeps native defaults. Legend overrides do not rename the Viewer's Lens/finder kind catalog, and lifecycle's separate final-state legend item is not overridden by these entries. Inspect the rendered result and review the meanings; a label is not a business approval.

The authored source spec for a public workflow is restricted to root keys `schema_version`, `diagram_type`, `meta`, `lanes`, `nodes`, `edges`; lane keys `id`, `label`; node keys `id`, `lane`, `col`, `type`, `label`, `width`; and edge keys `id`, `from`, `to`, `label`, `role`, `route`. For lifecycle the source root is restricted to `schema_version`, `diagram_type`, `meta`, `mainPath`, `states`, `transitions`; state keys `id`, `type`, `label`, `sublabel`, `tag`, `step`; transition keys `id`, `from`, `to`, `label`. These are permitted keys, not a statement that all are required; the native schema still applies. Source `meta` is not copied. A source-shape error under `/disclosure/views/.../source` identifies the authored `/nativeViews/.../spec` path and unsupported keys in its evidence: it is not a missing disclosure-policy `source` property. Keep richer internal views intact; if needed, author and review a separate compatible native view as project data rather than silently dropping cards or other source content. Public views are freshly prepared by the native renderer from the approved public labels and structural subset; no source title, subtitle, legend, paths, raw native HTML, overlays or reverse map is copied. Unsupported native details fail closed where required; source metadata is not a public input. The public specification and bindings are identity-bound for reader, Markdown assets and feedback mapping. Keep the complete source and policy privately for mapping and review.

The reader previews explicitly authored questions concerning the current object. It uses the question's disclosed `detail.scope` or a disclosed typed `target` relation; when both are present, only their intersection qualifies. Disagreement does not establish a link. A question preview is context, not a dependency, decision or approval. Client previews use only projected questions and approved public aliases; omission explanations are not identifiers and cannot create links. Back, deep links and native-focus restoration use the same bounded navigation rules.

Search does not treat the first or current service as an owner for shared objects. For a shared rule, explicitly scoped activities or interfaces used by owned activities may establish navigation context. Questions, evidence, decisions and sources use the prepared service-evidence associations; shared interfaces, fields and bindings use prepared activity usage. Ambiguous or unsupported context requires an eligible service or remains unavailable. An unassociated project-wide source can be inspected from an already selected service, clearly labeled as viewing context only; the catalog does not assign it a service. A project with explicit research associations also has a read-only Project research catalog entry, including without a Service: extension notes must explicitly target the project; scoped/targeted questions and source-provenance links are followed from reached project research records, including sources and questions, without inferring Service ownership. Search and project deep links do not infer a project from unassociated material; shared research requires selecting an eligible project. Local feedback comments remain a separate browser journal, not source capture or a model change. Client navigation uses only disclosed projection data. This usage context does not change canonical ownership.

Several native nodes may legitimately bind one model object. After a validated native activation, the reader returns focus to the exact invoking node on Close, Escape or back to the native view, including nested navigation in the same frame. This is transient navigation context, not a separate business activity or a change to the model. View/frame changes invalidate old native focus context; search and fresh deep links do not inherit an earlier native invoker.

## Feedback and explicit changes

A model needs a stable lowercase UUID v4 `workspaceId` to accept feedback. Browser comments are unauthenticated inert data, not instructions, patches or approvals. Local browser journals depend on storage origin/profile and can be lost; explicitly download JSON to transfer or back up. Client and internal journals and package kinds are separate. Never upload an internal package to a client reader.

```sh
node bin/archify.mjs prd feedback validate PACKAGE.json --json
node bin/archify.mjs prd feedback map-public PUBLIC.json --model MODEL.json --disclosure POLICY.json --expect-revision REVISION --expect-snapshot SNAPSHOT -o NEW_INTERNAL_PACKAGE.json --json
node bin/archify.mjs prd feedback import NEW_INTERNAL_PACKAGE.json --model MODEL.json -o NEW_STORE.json --json
node bin/archify.mjs prd feedback inspect NEW_STORE.json --model MODEL.json --json
node bin/archify.mjs prd feedback export STORE.json -o NEW_PACKAGE.json --json
```

For public mapping, retain the exact source model, assets, policy and public revision/snapshot. Mapping reconstructs and verifies the projection; stale, missing or ambiguous aliases fail closed. Each mapped comment retains public origin and its complete source snapshot in the private package/Store. Different public wording is `needs-review`, not silently rewritten. When extending a Store, supply `--store STORE.json --expect-store STORE_REVISION`; conflicting same-ID content is rejected. Inspect before acting. Source and image anchors must still match. Receipts and mapped Stores are private authoring material.

A proposal is an explicitly authored `archify-prd-change-request` JSON object, not something extracted from comments. It names `workspaceId`, `proposalId`, exact `baseRevision` and `storeRevision`, `objectId`, `operation`, allowed `path`, exact `oldValue`, `oldHash` (SHA-256 of UTF-8 canonical JSON, recursively sorted object keys and preserved array order), `newValue` and current `commentIds`. Use `replace` for an allowed existing property. For decision correction, use `operation: "decision-correction"`, `path: "/decision/supersession"`, the original decision's complete canonical JSON string as `oldValue`, and a JSON string for a new proposed decision with a distinct ID, the same scope and a typed `supersedes` reference. Its other references may only be `derivedFrom`; the original decision is retained. Then explicitly propose and apply:

```sh
node bin/archify.mjs prd feedback propose REQUEST.json --model MODEL.json --store STORE.json --expect-store STORE_REVISION -o NEW_PROPOSAL.json --json
node bin/archify.mjs prd feedback apply PROPOSAL.json --model MODEL.json --store STORE.json --expect-store STORE_REVISION -o NEW_MODEL.json --json
node bin/archify.mjs prd compile NEW_MODEL.json -o NEW_MANIFEST.json --base-manifest OLD_MANIFEST.json --expect-revision OLD_REVISION --json
```

The new model must be written beside the original so relative assets remain valid. Applying records technical lineage and marks affected dependents for review; it does not confer business confirmation or clear review flags. For v2, a proposal or apply can save a candidate with located stale-summary and stale-standard-text warnings without refreshing any authored text or hashes. The resulting model still fails ordinary validation and compilation until an author reviews the affected text and explicitly updates its bindings; retain the original feedback Store and history. Other candidate errors remain failures. Read diagnostics for allowed paths, scope, size limits and missing facts. These feedback workflows do not implement a business-approval process; Service-export caching is a separate mechanism described above.
