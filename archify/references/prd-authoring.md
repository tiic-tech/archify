# Research and progressive PRD authoring

Use the same versioned Archify workspace from research through native canvas and deliverables. An Agent interprets the actual material; the CLI checks and projects authored facts. Neither binary-file ingestion nor semantic truth is automatic. Read [PRD workspace](prd-workspace.md) for commands, v2 review helpers, Service packets, client disclosure and feedback; consult `schemas/prd-workspace.schema.json` for closed shapes. Examples demonstrate contracts, not requirements to copy.

## Start with incomplete evidence

Copy [`examples/prd-research-starter.json`](../examples/prd-research-starter.json) into the project's own version-controlled working folder. Replace its illustrative material and IDs; generate a new lowercase UUID v4 `workspaceId` for the new workspace, then keep it stable. Record each source's `recordKey`, `version`, locator, exact text and SHA-256 of its UTF-8 text. A source ref uses an exact contiguous quote, locator and interpretation; retain the original file separately when appropriate. Preserve observed reference-system field values as quoted reference facts, not approved values for a new target product; when target behavior is unconfirmed, use the existing scoped question-bound target cells. Keep unknown material as `extension` with an explicit typed `target` relation to the project, not an invented parent, and attach source refs. Put a scoped `question` on the relevant project, source or observation; if both `detail.scope` and `target` exist, their intersection establishes reader context. Record what remains unknown and who can clarify it; do not invent an activity, role, Service or screen to make a draft look complete.

Replace `SKILL` below with the absolute path to the packaged Skill and use new output paths. The example's extension warning is expected; its research scope is not ready (it lacks a backend contract and acceptance case) and still has a blocking question. Validation/compilation/build are not confirmation.

```sh
cp "$SKILL/examples/prd-research-starter.json" workspace.json
node "$SKILL/bin/archify.mjs" prd validate workspace.json --json
node "$SKILL/bin/archify.mjs" prd compile workspace.json -o baseline-manifest.json --json
node "$SKILL/bin/archify.mjs" prd build workspace.json -o baseline-reader.html --audience internal --json
# A separate readiness check is expected to fail while its blocking question remains:
node "$SKILL/bin/archify.mjs" prd compile workspace.json -o ready-manifest.json --ready project --json
```

The source JSON, native specs and assets are authoritative; a reader, Markdown/HTML/PDF and frozen package are derived outputs. Internal sources and readers may contain confidential material. Do not share them as public artifacts.

## Grow the graph and Feature

1. When the evidence establishes a boundary, add a `service` under a `project`. An activity belongs under a Service, journey or phase; a journey belongs under a Service or role. Model human, system and external work only when supported. An activity's `actor` points to a role, `uses` to an interface, `action`/`integration` to actual operations and `next` to an activity. For authored `parent`, runtime permits: document/service → project; capability → service/capability/taxonomy; taxonomy → project/taxonomy; journey → service/role; phase → journey/service; activity → phase/journey/service; section → interface/section; variant → interface; element → section/interface/variant; binding → section/interface/variant/activity; state/transition → entity. Section, variant, element, binding, state and transition require a parent; a binding has exactly one `field` relation and may have a `rule`. Types not listed do not accept a parent. The schema's general parent string does not by itself establish a valid relationship; use typed relations, not fictitious containment.
2. Author a source-anchored native workflow in `nativeViews`: bind operation nodes to activities and lanes to roles, preserving participant handoffs, branches and outcomes. A business-condition node may instead bind a typed `rule` explicitly scoped to the workflow Service or a bound activity; it is a constraint, not an actor, action or numbered activity step. Do not invent an operation to represent a rule. Reconcile edges through condition nodes with modeled `activity.next` where known; neither is automatically rewritten from the other. Leave incomplete outcomes or unknown conditions explicitly unresolved rather than inventing transitions. A `detailed` v2 Feature selects one existing full-process workflow and actions for its actual activities. A human action may reference a used page/variant; system or external work can be page-free. Do not fabricate screens for automated processes. Use the `catalog-only` Feature and a scoped question where detail is not yet modeled.
3. Opt into the closed standard extension with `profile.productDocument.standard.version: 1` and the root's reviewed metadata/history, plus `standard` on every selected Feature. The complete synthetic [`prd-equipment-standard-workspace.json`](../examples/prd-equipment-standard-workspace.json) shows the actual shape; `standardDocumentV1`, `standardFeatureV1` and their referenced schema definitions are authoritative. Each detailed Feature has the ordered Description, Preconditions, Postconditions, Role based workflow map, Prototype with UI elements & rules, Integration points, Audit & Security, and Acceptance Criteria sections. Use reviewed `{text, reviewed}` facts or `{question: "questionId"}` at each supported fact location; questions must apply to that scope.
4. In the workflow map, each step binds `number`, native `node`, `activity`, `role`, and a screen `S1` or process `P1` block. Author its specific action and response for that occurrence: distinct retry, failure and return nodes must not inherit identical activity prose blindly. In the prototype section, an `S` screen binds the actual Feature page/interface/variant, fields and bindings; a `P` process records trigger, input, processing, output and exceptions. Keep each path distinct and write concise observable criteria with actual source, step, block, rule, transition or exception references. Do not manufacture UI, default values, access rules or success paths.
5. A standard field's `dataType` and `required` must agree with the known canonical field and binding; unknown canonical values cannot be promoted to known presentation values. For reuse define a `businessRules` entry once in its owner Feature, bound to the canonical `rule`, with relevant steps/bindings and reviewed or question-bound rule cells. A local reference is `"BR-1"`; another Feature refers to `{ "feature": "ownerFeatureId", "id": "BR-1" }`. Reuse does not duplicate the owner Feature or authorize private dependencies in client output. Missing required cells block the relevant readiness scope.

## Continue a baseline today

Keep the model, native specifications, local assets, source versions and authored profile in the project's Git history. Record the baseline compile receipt and manifest. Preserve IDs for the same meaning, append a new source object/version rather than replacing the earlier source, preserve existing history prefixes, and link new evidence. Review the affected graph facts, `activity.next`, native topology/bindings, Feature steps/blocks, criteria and the affected authored summaries together. Explicitly review prose and its cited facts before refreshing their snapshots; bulk rehashing is not review. Keep old client policy and asset approvals separate: change requires a fresh public review and approval where the contract detects staleness.

```sh
node "$SKILL/bin/archify.mjs" prd validate workspace-next.json --json
node "$SKILL/bin/archify.mjs" prd compile workspace-next.json -o next-manifest.json \
  --base-manifest baseline-manifest.json --expect-revision BASELINE_REVISION --json
```

Keep old immutable outputs and use new paths; a cold compile alone cannot check ancestry. Service incremental export has its own verified base and history prefix; see [Service packets](prd-workspace.md#service-scoped-markdown-and-authored-history). Current reviewed feedback operations support allowlisted property replacement or decision supersession, not arbitrary source/node/view/asset/profile changes. The offline browser is read-only for model authoring: its local comments are a separate, losable journal and require explicit JSON transfer and review. It does not provide durable canvas editing, autosave or cloud concurrency. Those are later capabilities, not implied by these commands.
