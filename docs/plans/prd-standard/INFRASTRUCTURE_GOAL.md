# PRD authoring infrastructure — acceptance boundary

The product end state and current slice are defined in [PRODUCT_GOAL.md](PRODUCT_GOAL.md): an integrated canvas workspace across product development. Archify and this development form one product. Reusable PRD authoring/export is one infrastructure capability within that workspace. A private pilot is test data, not the implementation boundary or a one-time document deliverable. Passing one pilot does not establish the product outcome.

Future product separation is not a requirement to remove Archify or build a standalone export kernel. Preserve and extend the integrated native capabilities; verify the workspace lifecycle.

## Reusable path

A fresh Agent, using the generic installed Skill, schema, public examples and supported helpers, must be able to take a new project's supplied materials through evidence intake, a project-neutral structured workspace, explicit gaps, standard PRD generation, iteration and audience-specific delivery. It must not require a private pilot repository, its paths, names, Service IDs, authoring recipe, disclosure policy or reference documents. Domain facts belong to that project's workspace and source evidence.

The deterministic renderer consumes validated structured data; an Agent performs source interpretation and authoring. Do not claim that a layout checker proves requirement truth, that every binary format is natively parsed, or that missing facts can be filled without evidence. Document supported intake tools/adapters and limits. Sparse material must yield a useful research draft with located questions and readiness failure, not invented complete requirements.

The supplied fixed PRD standard is the generic presentation contract. The source model remains versioned and authoritative; Markdown is primary derived output. HTML, PDF, native views and frozen reader packages share the validated version and composition path. Module/Feature hierarchy, participant workflows, screens, system processes, fields, rules, evidence and decisions remain project data. Common semantics must not be encoded with one domain's constants.

## Cross-project acceptance

Verify source-backed generation from at least two unrelated project domains and an additional sparse-input case, with contrasting material and process shapes:

- A human/external-participant workflow with pages, form controls, alternatives and a supplied image or design gap.
- An automated/integration-heavy workflow, including P-only work, failures, named rule/example and external system handoff; do not invent a user page.
- Incomplete requirements with unknown roles/rules/fields/states, explicit questions and honest draft/readiness behavior.

Use independently authored synthetic raw materials (for example briefs/meeting notes, tabular field dictionaries, structured interface facts and an image) with inspectable source locators, not only variations of an already typed JSON fixture. The generic Skill must describe the normalization/authoring path. Validate expected facts and omissions against the corpus; semantic/source review is separate from the structural checker. Do not hardcode any reference PRD's business content into the generic schema or composer.

Iterate one corpus after its first export: update a rule or field contract, add a scoped question, revise a workflow branch and supply a later design asset. Verify dependency propagation, stable identities, unchanged-block/resource reuse, cold/warm equality, authored version-log prefix, stale-public protection and external-edit conflict preservation. Verify an unrelated project's outputs remain isolated.

Retain the private pilot as an additional real-world boundary test and source-quality assessment. Project-specific data corrections are not substitutes for implementation or regression coverage. Private evidence stays private; the public repository and Skill use synthetic/general material only.

## Release acceptance

Independent source/diff review, appropriate successful checks against the final revision, public disclosure/asset closure, current reader/download/print behavior, exact tracked package contents and installation/deployment receipts are required. A standalone report or a single well-formatted document cannot close this work. Preserve branch/commit/PR lineage, deployment rollback and reusable new-Session instructions. State remaining business gaps separately from technical acceptance.
