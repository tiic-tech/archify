# Structured PRD profile: schema checkpoint

**Implementation in progress; not an export contract yet.** The closed draft-07 shapes are in `archify/schemas/prd-workspace.schema.json`, definitions `standardDocumentV1` and `standardFeatureV1` and their `standard*V1` dependencies. The unrelated synthetic draft is `archify/examples/prd-equipment-standard-workspace.json`; the prior `archify/examples/prd-equipment-workspace.json` remains a usable v2 example. The new example passes draft validation but not readiness. It deliberately includes unresolved questions, a missing screen and an incomplete status model. Its fictional release entries illustrate structure, not approval or real history.

The normal PRD validator runs the existing v2 checks and the standard checks; unresolved questions may pass draft validation but block readiness. Internal and explicitly approved public standard composition have an initial shared-IR path. This is not yet a delivery contract: semantic review of prose, broader consumer integration and independent review remain open. Do not assume validation establishes truth, business confirmation or a complete review of native diagram meaning. No ZIP refresh or installation is part of this checkpoint.

## Placement and reuse

A workspace remains `schemaVersion: 1` and retains `profile.productDocument.version: 2`. Add `profile.productDocument.standard` with `version: 1`. Every Feature in its existing `modules[].subModules[].features[]` hierarchy must then have a `standard` object; the schema rejects either a partial opt-in or a Feature extension without the document extension. Existing v2 fields (`id`, `key`, `title`, `service`, `status`, `summary`, `workflow`, `actions`, pages and groups) remain the canonical graph/presentation references. V1 and v2 without the extension retain their previous shapes. The new profile uses the existing Feature as the document sub-module; the existing `subModules` layer remains editorial grouping, not another document heading by default.

All new prose cells are **facts**: either the existing v2 reviewed text shape `{ "text": "...", "reviewed": [{ "object": "objectId", "sha256": "<64 lowercase hex>" }] }` or a gap `{ "question": "questionId" }`. A gap refers to an existing modeled question scoped to the affected context; it is not the text `TBC` or an invented answer. `standardFactsV1` is a nonempty array of these. Review entries must ultimately cover the transitive semantic dependencies, using audience-specific facts and hashes; public text and references require an independently authored and allowlisted public plan. The example uses `snapshotReviewedTextV2` for its internal reviewed cells. Rehashing without reviewing text is not confirmation. IDs in the shape are source model IDs unless identified as local step/block IDs below; public export must remap IDs and must not fall back to private material.

## Document metadata

`productDocument.standard` contains:

- `version: 1`; `title`, `startDate`, `documentVersion`, `background` as facts; `authors`, `reviewers` as fact arrays.
- `objectives`: 3–6 `{goal, meaning}` fact pairs. Optional `glossary` is an array of `{term, definition}` fact pairs; an unknown definition is a scoped question gap, not an invented expansion.
- `roles`: `{role, purpose, permissions, restrictions}` where `role` is a typed role object ID and the other values are facts. Unknown permissions remain gaps, not grants. `sharedRules`: `{rule, description}` referring to an actual typed rule. General Module presentation must use only this modeled context; it must not invent login or role-management functionality.
- `history`: oldest first, each `{version, date, change, author, released, references, chapters}`. `version` is authored text, `date`, `change`, `author` are facts, `released` is boolean, `references` is an array of facts, and `chapters` is an array of `{feature, summary}` (Feature presentation ID and fact). Post-v1.0 release entries need explicit references and one chapter summary for each changed Feature. A Feature's matching `changes` entries contain `{version, references, items}` with nonempty fact arrays. The eventual semantic validator must enforce release ordering, matching chapter/callout content and version rules; the schema alone cannot establish these. A Service packet is a scoped extract of the master document: its separately supplied Service history must retain the actual prefix, and whole/reader exports must not invent a Service log.

## Feature specification

`feature.standard` is `{priority, readiness, featureDescription, note, changes, sections}`. Priority is `P0`, `P1`, `P2`, or a question gap; readiness is `High`, `Medium`, `Low`, or a question gap. Description and note are facts. `sections` is an **ordered array of exactly eight closed objects** with the following exact `section` discriminators and members:

1. `Description`: `content` fact.
2. `Preconditions`: `conditions` fact array; each must be checkable or a scoped question.
3. `Postconditions`: `success`, `rejection`, `cancellation`, `failure` fact arrays, including explicit not-applicable facts or gaps where appropriate.
4. `Role based workflow map`: `steps`, `statusModel`, optional `question`. A step has `{number,node,activity,role,block,action,response,rules,businessRules}`. `number` is a local `1`, `2`, `3a`-style identifier; `node` refers to a node of the Feature's existing native workflow; `activity` and `role` are modeled IDs; `block` is an `S1`/`P1`-style local ID. `action` and `response` are facts, `rules` a fact array, and `businessRules` references as described below. An empty step array requires a scoped `question`. `statusModel` has `completeness: "complete" | "incomplete"`, `states: [{state,meaning,initial}]` and `transitions: [{transition,from,to,step,role,action}]`; state and transition values are typed modeled IDs, `step` is the local number, and meaning/action are facts. An incomplete model requires `question` and is not a whitelist or ready. Later validation must check endpoint types, reachability, native branches and agreement, rather than inferring missing states.
5. `Prototype with UI elements & rules`: `screens`, `processes`, `businessRules`, in that output order. A screen is either `{kind:"screen",id,page,interface,variant?,design,assets,elements,pageRules,fields,buttons,messages}` or the mutually exclusive `{kind:"missing-screen",id,question}`. `page` is an existing v2 action page anchor; `interface`, optional `variant`, `assets`, `elements` and button references are actual modeled IDs. `design`, `pageRules`, `messages` are facts/fact arrays; `design` may describe a supplied route, never an inferred one. A button is `{element,action?,visibility,enabled,behavior}` with fact-valued descriptions. A field row is either `{field,binding,dataType,typeDetails,required,default,rules,source,editableWhen,businessRules}` or the closed unresolved-upload row `{element,question}`. The latter references an actual upload element on this page and a question scoped to that element; it must not imply a typed field or binding. It blocks readiness. For a specified field, field and binding are actual IDs, never predicate-only fields presented as controls; dataType and required use the closed schema enums or a question gap, and the other cells are facts. `typeDetails` supplies units, decimal precision, attachment constraints, lookup target or ID format when applicable, as reviewed facts or gaps. Optional `actionMatrix` rows are `{state,role,actions,condition?}`: state and role are modeled IDs, actions are actual page element IDs or their modeled action IDs, and the optional condition is a fact.

   A process is `{id,title,trigger,input,processing,output,exceptions,volumeTiming,humanCheckpoint,integrations,notifications,businessRules}`. Title and all seven spec cells are facts; `exceptions` is a nonempty list of `{id,description}` with local IDs and fact descriptions. Integration IDs refer to typed integration objects; notification IDs refer to the local notification rows below. Across steps, fields, processes and criteria, `businessRules` entries are either local `"BR-1"` strings or qualified `{feature, id}` objects identifying the owning Feature presentation ID and its local BR ID. The owner authors the only definition. References must resolve to a typed rule applicable to the using Feature; a public plan must independently approve the owner, rule and source closure. A BR is `{id,rule,name,steps,bindings,appliesTo,inputs,logic,unitsRounding,boundaries,workedExample}`. `id` is a local `BR-1`-style ID; `rule` is a modeled rule ID; `steps` and `bindings` identify its actual application; all other members are facts. Unknown formulae and examples are gaps, not guessed policy.
6. `Integration points`: `integrations`, `notifications`, optional `none` fact. Integration rows are `{integration,direction,trigger,data,timing,failure}` with a modeled integration ID and fact cells. Notification rows are `{id,event,channel,recipient,roles,integration?}`, using a local notification ID, fact cells and actual role/integration IDs. Empty arrays alone do not prove that an integration or notification is unnecessary; the author must supply an applicable `none` fact or gap and later validation must enforce that distinction.
7. `Audit & Security`: `audit`, `access`, `integrity` fact arrays. They state modeled behavior or scoped gaps, not invented access policy.
8. `Acceptance Criteria`: `criteria` array. Each row is `{id,observation,sources,steps,blocks,businessRules,transitions,processExceptions,coverage}`. `observation` is a fact; `sources` and `transitions` are modeled IDs; the other references are local identifiers. `coverage` uses the schema's closed labels for path, field, process trigger/output/exception, rule example, integration, access, audit and integrity. Later semantic validation must verify real source and path coverage and locate gaps rather than accepting labels as proof.

For the in-progress public standard path, a selected screen asset is approved privately as `assets: {sourceAssetId: {id, caption, sha256, version}}`. Its source asset must have that explicit version and exact SHA-256, be distributable, be attached to the selected projected interface or variant, and contain an allowed image. The hash and version bind the approval to the supplied bytes; replacing an image requires a new explicit approval. Historical and legacy v1/v2 attachments retain their existing `{id, caption}` policy. This is an initial client-projection path, not an accepted public delivery contract; independently review the resulting artifacts and the remaining consistency limitations.

The public projection matches each screen to a unique canonical Feature by Service, native workflow, activity, interface and variant, then matches fields by binding and field. Known public datatype and requiredness must match the canonical standard values; canonical gaps cannot become known public values. A public matrix row must be covered by one canonical row for the same screen, state and role, with all its actions and without dropping a condition or converting an unknown condition into known text. Public gaps remain possible. This check does not establish that independently authored condition prose has equivalent meaning or that any reviewed prose is true; those remain human review responsibilities. It neither hashes private standard prose into public reviews nor reapproves public facts.

The production API `validatePrd(model)` retains v2 validation and invokes `validateStandardDocumentV1(model)` from `archify/explainer/workspace/prd-standard-v1.mjs`; the latter calls `validateStandardRefinementsV1` for the refined references. `readiness(model, scope)` also invokes `standardReadinessV1` for scoped authored gaps. These are technical checks, not proof that every business alternative is represented or that a diagram communicates the intended business policy. The internal shared IR and numbered native diagrams have an initial implementation, and new runtime modules are included in preparation identity and clean-staging requirements. Service extracts carry the minimal referenced external rule definitions and question context from the validated master audience plan in a nontransactional catalog, with qualified links; they do not include the owner Feature as a Service Feature. Relevant definitions participate in the Service identity. Incremental identities and conflict handling beyond this closure, broader Service/reader/export tests, and package/installed-reference refresh remain required before delivery.
